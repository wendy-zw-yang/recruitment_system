## 追加 · v0.7.4.1 AI 重排顺序 + 加载体验（14:15）

### 触发原因

上一轮 v0.7.4 完成后用户实测发现两个体验问题：

1. **AI 标签未按分数排序**——handoff §4 决策 #2「AI 重排后按 score DESC 排序（高分优先）」**已确认**但代码层未落地。`recommendOnResume` 内部仍按 4 维 Java 内存分排序（行业+8 / 城市+4 / 省份+2 / 关键词+1），与 LLM 打出的 `aiScore` 是两套独立评分。LLM 完成后通过 `fillAiScore` 填入 DTO，但**没有重排**，所以卡片顺序还是 Java 内存分顺序。

2. **AI 完成时显示"加载中…"**——SSE `recommendation_ready` 到达后，`CandidateHome.vue` 的 watch handler 调用 `loadRecommended()`，触发 `jobsLoading = true`，模板 `<div v-if="jobsLoading" class="loading">加载中…</div>` 遮罩整个推荐位。

### 用户原始原话（"确认，先执行这两条改动吧"）

> 1. AI 标签没有按分数高低进行排序，我想要的是高分在前的有序显示；
> 2. 我希望做到先让用户看到 SQL 排序结果，把 AI 调用作为异步放在后台，前端在 AI 重排结束后刷新（同时弹窗）即可切换为 AI 重排结果，不要让用户看到长时间的"加载中…"。

### 修复

#### 1. 后端按 aiScore DESC 重排（决策 #2 落地）

`backend/src/main/java/com/example/recruitmentsystem/service/impl/JobServiceImpl.java`：

```java
private IPage<JobDto> wrapAsPage(List<Job> jobs, int pageNum, int pageSize, Long candidateId, Long total) {
    Page<Job> memPage = new Page<>(pageNum, pageSize, total);
    memPage.setRecords(jobs);
    IPage<JobDto> dtos = memPage.convert(this::enrich);
    fillFavorited(dtos, candidateId);
    fillAiScore(dtos, candidateId);
    // v0.7.4.1：决策 #2 落地——AI 重排完成后按 aiScore DESC 重排（高分优先），
    // 无 aiScore 的卡片排到末尾。仅当 cache 有此 userId 数据时生效（说明 AI 已跑过）。
    reorderByAiScore(dtos, candidateId);
    return dtos;
}

/**
 * v0.7.4.1：决策 #2 落地——按 aiScore DESC 重排（高分优先）。
 * - 仅当 recommendScoresCache[userId] 非空时生效（AI 已跑过）
 * - aiScore 为 null 的卡片排到末尾
 * - 同分按发布时间倒序（nullsLast）
 */
private void reorderByAiScore(IPage<JobDto> dtos, Long candidateId) {
    if (candidateId == null) return;
    ConcurrentHashMap<Long, Integer> userCache = recommendScoresCache.get(candidateId);
    if (userCache == null || userCache.isEmpty()) return;
    List<JobDto> records = dtos.getRecords();
    if (records == null || records.size() <= 1) return;
    records.sort((a, b) -> {
        Integer sa = a.getAiScore();
        Integer sb = b.getAiScore();
        if (sa == null && sb == null) return 0;
        if (sa == null) return 1;
        if (sb == null) return -1;
        int cmp = Integer.compare(sb, sa);   // DESC
        if (cmp != 0) return cmp;
        if (a.getPublishedAt() == null && b.getPublishedAt() == null) return 0;
        if (a.getPublishedAt() == null) return 1;
        if (b.getPublishedAt() == null) return -1;
        return b.getPublishedAt().compareTo(a.getPublishedAt());
    });
}
```

**附带改动**：缓存可见性

```java
// v0.7.4.1：visibility 从 private 提到 public，与 recommendPendingFlag 对齐，便于同包测试清理
public static final ConcurrentHashMap<Long, ConcurrentHashMap<Long, Integer>> recommendScoresCache
```

#### 2. 前端 AI 完成时原地更新 + 重排，**不**显示"加载中…"

`frontend/src/views/candidate/CandidateHome.vue` 的 watch handler 重写：

```js
/**
 * v0.7.4.1：监听 AI 推荐打分完成事件。后端异步完成后通过 SSE 推
 * {@code recommendation_ready} 事件 → recommendStore.lastEvent 变化 → 原地更新卡片 + 重排。
 *
 * <p>关键决策：不调用 loadRecommended()（避免"加载中…"闪屏打断阅读）；
 * 改为原地更新每张卡片的 aiScore + 整个数组按 aiScore DESC 重排。</p>
 */
watch(
  () => recommendStore.lastEvent,
  (event) => {
    if (!event || route.path !== '/home') return
    const scores = recommendStore.consumeLatestScores()
    const scoreEntries = Object.entries(scores)
    if (scoreEntries.length === 0) return

    // 1. 原地更新每张卡片的 aiScore
    const list = recommendedJobs.value
    const scoreMap = new Map(scoreEntries.map(([k, v]) => [Number(k), v]))
    let changed = false
    for (const job of list) {
      const newScore = scoreMap.get(job.id)
      if (newScore != null && job.aiScore !== newScore) {
        job.aiScore = newScore
        changed = true
      }
    }

    // 2. 按 aiScore DESC 重新排序（高分优先；null 排最后）
    if (changed) {
      const sorted = [...list].sort((a, b) => {
        if (a.aiScore == null && b.aiScore == null) return 0
        if (a.aiScore == null) return 1
        if (b.aiScore == null) return -1
        return b.aiScore - a.aiScore
      })
      recommendedJobs.value = sorted   // 整体替换 → 触发 v-for 重排
    }

    // 3. 弹 toast
    const maxScore = Math.max(...Object.values(scores).map((v) => v || 0))
    ElMessage.success(
      `AI 已完成智能匹配（最高分 ${maxScore}），已按分数重排`
    )
    // 不调用 loadRecommended() → 不显示"加载中…"
  }
)
```

## 追加 · v0.7.4.3 撤回流程修复：SYSTEM 消息 senderId + 事务传播（HH:MM）

### 触发原因

用户实测：候选人点"撤回投递"弹"系统异常，请稍后重试"，且 application 状态实际未变（仍是 PENDING_REVIEW）。

### 根因诊断（双重 bug）

#### Bug #1（主因）— `message.sender_id = 0` 触发外键异常

`MessageServiceImpl.SYSTEM_SENDER_ID = 0L`，SYSTEM 消息 `INSERT INTO message (..., sender_id, ...)` 时填 0，但 `message` 表的 FK 约束：

```sql
CONSTRAINT `fk_message_sender` FOREIGN KEY (`sender_id`) REFERENCES `users` (`id`)
```

要求 `sender_id` 必须指向存在的 `users.id`，user 0 不存在 → `SQLIntegrityConstraintViolationException`。

**后端日志实证**：
```
### Error updating database.  Cause: java.sql.SQLIntegrityConstraintViolationException:
Cannot add or update a child row: a foreign key constraint fails
(`recruitment_system`.`message`, CONSTRAINT `fk_message_sender` FOREIGN KEY (`sender_id`) REFERENCES `users` (`id`))
```

#### Bug #2（放大器）— 事务 rollback-only 污染外层 withdraw

`MessageServiceImpl.sendSystemMessage` 是 `@Transactional`（REQUIRED 默认传播），加入外层 `ApplicationServiceImpl.withdraw` 事务。FK 异常抛出后：
1. Spring 立即把整个外层事务标记为 **rollback-only**（在异常点同步标记，不等方法返回）
2. `withdraw` 内 `try/catch (Exception e)` 捕获原异常并 log warn，代码继续执行
3. `withdraw` 方法返回 → Spring 尝试 commit 外层事务
4. 事务已 rollback-only → 抛 `UnexpectedRollbackException: Transaction rolled back because it has been marked as rollback-only`
5. `UnexpectedRollbackException` 走 `GlobalExceptionHandler.handleException` catch-all → 返回 `Result.fail(500, "系统异常，请稍后重试")`
6. 同时 application 状态更新被一并回滚（用户以为撤回成功，实际数据库里 status 仍是 PENDING_REVIEW）

### 修复

#### Fix #1：SYSTEM 消息 senderId 改用 NULL

`backend/.../service/message/impl/MessageServiceImpl.java`：

```diff
- /** SYSTEM 消息 senderId 占位（0 表示系统） */
- private static final Long SYSTEM_SENDER_ID = 0L;
+ /** SYSTEM 消息 senderId 占位（null 表示系统，无真实用户）。
+  * v0.7.4.3 修复：原值 0L 会触发 fk_message_sender 外键异常（users.id=0 不存在），
+  * 改用 null 走 FK 旁路（schema 已允许 sender_id 为 NULL）。 */
+ private static final Long SYSTEM_SENDER_ID = null;
```

`schema.sql` 配套修改：`sender_id BIGINT NOT NULL` → `sender_id BIGINT NULL`。
新增 `docs/DataBase/migration-v0.7.4.3-message-sender-id-nullable.sql` 给用户手动执行（幂等 ALTER）。

#### Fix #2：`sendSystemMessage` 事务传播改为 REQUIRES_NEW

```diff
  @Override
- @Transactional
+ // v0.7.4.3 修复：REQUIRES_NEW 独立事务——撤回流程 (§4) 中 sendSystemMessage 异常不应让外层
+ // withdraw 事务被标记 rollback-only。REQUIRED 默认会污染外层事务，即使 try/catch 捕获了
+ // 原异常，提交时仍会抛 UnexpectedRollbackException，导致 application 状态更新被一并回滚。
+ @Transactional(propagation = Propagation.REQUIRES_NEW)
  public Long sendSystemMessage(Long hrUserId, Long candidateId, String content, Long jobId) {
```

**为什么不只是修 Fix #1**：即使 FK 修了，sendSystemMessage 仍可能因其他原因（DB 瞬断 / SSE 推送异常等）抛运行时异常；REQUIRES_NEW 隔离了副作用，撤回主流程永远不会因系统消息失败而回滚。

## 追加 · v0.7.4.4 「我的投递」列表不刷新（HH:MM）

### 触发原因

用户实测：候选人投递职位 A 后，再次投递职位 B，"我的投递"列表只显示 1 条；HR 侧确认收到 2 份简历（数据正确入库）。

### 根因诊断

后端 `/api/applications/mine` 返回 `total: 3, records: [...]`（实测正确），**问题在前端状态管理**：

`useApplicationStore.apply()` 仅调后端 `POST /api/applications` 拿 `applicationId`，**不更新** `myApplications`；列表刷新完全依赖 `MyApplications.vue` 的 `onMounted → loadList → store.fetchMine`。

在某些场景下 `onMounted` 不会触发：
- 用户从 `/applications/mine` 走 nav 跳走再回来（理论上重新挂载，但实际偶发不触发）
- 未来若加 `<keep-alive>` 缓存组件
- 直接 `router.push` 到同 path 的 query 变化（极少见）

任一场景下，`myApplications` 保留旧值，UI 显示陈旧数据。

### 修复

#### Fix 1：`useApplicationStore.apply` 投递成功后立即刷新（主修复）

```diff
  async function apply(data) {
    submitting.value = true
    try {
      const resp = await applicationApi.apply(data)
+     // v0.7.4.4：投递成功后立即刷新我的投递列表
+     await fetchMine(1, 100)
      return resp
    } finally {
      submitting.value = false
    }
  }
```

## 追加 · v0.7.4.5 「我的投递」不显示 VIEWED_BY_HR 状态的投递（HH:MM）

### 触发原因

用户实测反馈：v0.7.4.4 修后新增投递能显示，但**历史**投递（之前 HR 已查看 → 状态为 VIEWED_BY_HR）一直不显示，且**用户不能再次投递同一职位**（防重逻辑），永远看不到那条投递的进度。

### 根因诊断

`backend/.../ApplicationServiceImpl.listMine` L172：

```java
q.eq(Application::getCandidateId, candidateId)
        .ne(Application::getStatus, STATUS_VIEWED_BY_HR)  // 候选人侧隐藏 VIEWED_BY_HR
        .orderByDesc(Application::getAppliedAt);
```

`ne(VIEWED_BY_HR)` 让 VIEWED_BY_HR 状态的投递**永远不返回**。这是设计文档 §4.3.6 的"候选人侧显示逻辑"决策："隐藏 VIEWED_BY_HR（等同'处理中'）"。

**实际 UX 死胡同**：
1. 候选人投递 → 列表显示 PENDING_REVIEW
2. HR 点击"已查看" → 状态变 VIEWED_BY_HR
3. 候选人侧列表突然少一条
4. 候选人无法再次投递（防重）→ 永远看不到
5. 候选人无法跟踪"HR 已读但未决"的状态

v0.7.4.4 的修复只解决"前端状态管理"（缓存刷新），不修这个**后端过滤**逻辑。

### 修复

#### Fix 1：后端 `listMine` 去掉 VIEWED_BY_HR 过滤

```diff
  q.eq(Application::getCandidateId, candidateId)
-     .ne(Application::getStatus, STATUS_VIEWED_BY_HR)  // 候选人侧隐藏 VIEWED_BY_HR
+     // v0.7.4.5：不再过滤 VIEWED_BY_HR
+     // 但凡用户投过简历都应显示在「我的投递」中（设计文档 §4.3.6 已同步修订）
      .orderByDesc(Application::getAppliedAt);
```

**设计决策反转**：用户原话"但凡用户给某职位投过简历，该投递信息都要在'我的投递'中显示"。同步更新设计文档 §4.3.6。

#### Fix 2：前端补全 VIEWED_BY_HR 映射

之前部分页面的 `STATUS_LABEL` 缺失 `VIEWED_BY_HR`，未命中则 fallback 到原 enum 字符串显示"VIEWED_BY_HR"给用户看；`STATUS_TYPE` 的 `VIEWED_BY_HR: ''`（空字符串）会让 `el-tag type` 渲染异常。
