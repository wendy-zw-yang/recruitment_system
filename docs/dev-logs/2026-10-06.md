## 关键设计要点

### 1. 三条流路径

```java
// AiChatService.streamChat
1) 预校验（controller 层）：role + 空 + 长度
2) 写 USER 消息（持久化）
3) llmChatService.topK(question) → 是否命中
   - A. 命中（top-1 score ≥ 0.15）：llmClient.streamCall + 逐 chunk emit delta + 流完成写 ASSISTANT
   - B. 未命中：emit delta("抱歉,这个问题不在我能回答的范围内;请联系管理员") + 写 ASSISTANT + done + complete
   - C. LLM 失败：emit error 事件 + completeWithError
4) 不写 ai_call_log 的情况：B 路径（固定提示词不调 LLM）
```

### 2. 关键词检索算法

```java
// LlmChatService.tokenize（启动时一次性算好 section tokens；查询时 O(N)）
- 英文 / 数字词：[A-Za-z][A-Za-z0-9_]+（转小写）
- 中文字 char：char(单字)
- 中文 bigram：连续 2 字
示例：
  "如何投递" → {如,何,投,递,如何,何投,投递}

// 评分公式（每个 section 计算一次）
score(section, query) = |section.tokens ∩ q.tokens| / max(|q.tokens|, 1)
归一化到 [0, 1]；阈值 0.15；top-3

// 启动时
@PostConstruct init() → ClassPathResource("ai/manual.md") → 按 ## 切分 → List<Section>
// 每个 Section 在 init 时已 tokenize 为 Set<String>，查询时仅做 set 交集
```

### 3. AI-4 响应速度优化（用户高优先级）

| 优化项 | 实现 | 预期效果 |
|---|---|---|
| 流式输出 | `stream=true` + SSE | 首字延迟 3-5s → 0.5-1.5s |
| 短 prompt | top-3 section（~2000-3000 字）| 减少 input token |
| 短回答 | chat-max-tokens=600（中文 200 字 + buffer）| 减少 output token |
| 不强制 JSON | 聊天纯文本（去除 `response_format=json_object`）| 节省系统开销 |
| 独立 chat-model | LLM_CHAT_MODEL 可覆盖为 qwen-turbo | 用户可自行切换更快模型 |
| 关键词命中本地优先 | 不调 LLM 即可命中 | 0 token 消耗 + 0 网络延迟 |

### 4. SSE 事件协议

```
event: delta
data: {"text": "你好"}

event: delta
data: {"text": "，我是汇汇"}

event: done
data: {"sessionId": "uuid-xxx", "messageId": 123}

event: error
data: {"message": "客服暂不可用"}
```

边界兼容：`\n\n` 和 `\r\n\r\n` 都识别。

### 5. 流路径 B 决策（不调 LLM 节省 token）

```java
if (top.isEmpty()) {
    emitDelta("抱歉，这个问题不在我能回答的范围内；请联系管理员");
    saveMessage("ASSISTANT", canned);
    emitDone();
    // 不调 LLM，不写 ai_call_log
}
```

### 6. ADMIN 角色拒绝在 Controller 层

```java
@GetMapping("/stream")
public SseEmitter stream(...) {
    SseEmitter emitter = new SseEmitter(0L);
    try {
        if ("ADMIN".equals(CurrentUserContext.getRole())) {
            emitErrorAndComplete(emitter, "管理员无 AI 客服权限");  // 走 SSE error
            return emitter;
        }
        // ...其他校验同上
        aiChatService.streamChat(...);
    } catch (BusinessException e) {
        emitErrorAndComplete(emitter, e.getMessage());  // 不抛给 GlobalExceptionHandler
    }
    return emitter;
}
```

原因：SSE 通道已声明 `produces=text/event-stream`，GlobalExceptionHandler 返回的 `Result.fail(...)` JSON 无法写到该 Content-Type。直接走 SSE error 事件。

### 7. SSE 失败重试

前端 fetch error catch：
```js
.catch(err => {
  if (err.name === 'AbortError') return  // 用户主动停止
  onError(err.message)
})
```

流中断或网络异常时，前端 `asstMsg.error=true` 显示 **[出错] xxx**，用户可重新提问（新建请求即可，sessionId 复用）。

### 8. sessionId 策略

- 前端 UUID v4 生成（兼容 `crypto.randomUUID` 缺失）
- localStorage 持久化（key=`rs-ai-chat-session`）
- 关闭重开自动复用同一 sessionId → 历史自动恢复
- 用户点 "↻ 新建会话" → 重新生成 UUID，旧 sessionId 在后端仍然存在（可手动清空）
- 用户点 "🗑 清空历史" → 后端 `UPDATE is_deleted=1`，前端 chatHistory=[]

### 修复 2：SSE 异常逃逸（核心修复）

**问题机制**：
```
saveMessage 抛 BadSqlGrammarException
  → 走 [AiChatService] catch 块
  → emitErrorAndComplete(emitter, ...) 调用 emitter.send + emitter.complete
  → 但 Spring 异步机制仍把异常报告给 GlobalExceptionHandler
  → GlobalExceptionHandler 想写 Result.fail(500, ...) 到 text/event-stream
  → HttpMessageNotWritableException: "No converter for [class Result] with preset Content-Type 'text/event-stream'"
  → 前端 fetch 拿到不完整 / 异常响应 → onError 未触发 → typing 永闪
```

**v0.6.1 重构**：
- `AiChatService.streamChat` 顶层 try/catch(Throwable)，**保证永不抛异常**
- 移除 `emitter.completeWithError()`（会触发 GlobalExceptionHandler）
- 所有写入操作改用 `safeEmitDelta/safeEmitDone/safeEmitErrorAndComplete/safeComplete`，**失败仅记日志**
- 三个 catch 块嵌套：外层 Throwable 兜底 → 中层 Exception → 内层 BusinessException
- `AiChatController` 不再写 try/catch（依赖 service 不抛）

**回归测试**（`AiChatServiceTest.streamChat_saveMessageFailure_emitsErrorAndCompletes_noThrow`）：
```java
doAnswer(inv -> {

}).when(chatMapper).insert(any());

try {
    svc.streamChat(1L, "sid-dbfail", "如何投递", emitter);
} catch (Throwable t) {
    throw new AssertionError("streamChat 不可抛异常");
}
assertTrue(sentPayloads.size() >= 1);  // emit error 事件

// v0.6.1：增加 finished 标志 + chunk 计数
let finished = false
let gotAnyChunk = false

// 流正常结束但未收到 done/error → 视为完成（兜底）
if (!finished) {
  if (!gotAnyChunk) {
    finishWithError('连接中断，未收到回复')  // 真正异常
  } else {
    finishWithDone({ messageId: null, sessionId: null })  // 收到过内容但无 done → 当作完成

.catch(err => {
  if (err.name === 'AbortError') {
    if (!finished) {
      finished = true
      onDone({ aborted: true })  // 视为完成（用户停止），不报错
    }
  }
})

// reader.read 失败
} catch (readErr) {
  finishWithError(readErr.message || '流式读取失败')
}
```

### 关键设计要点

#### 1. 二元组唯一会话（用户最关注）

```
conversation (hr_user_id, candidate_id, is_deleted)  ← 唯一键
```

`ConversationServiceImpl.findOrCreate` 优先 `findByHrAndCandidate`；找不到才 `insert`。
撤回触发系统消息时，`MessageService.sendSystemMessage` 同样先 `findByHrAndCandidate`，不存在才创建。
→ **同一对 HR ↔ 候选人 永远只有一个有效聊天窗口**，无论候选人投了多少个职位。

#### 2. SSE 事务一致性

`MessageServiceImpl.pushAfterCommit` 使用 `TransactionSynchronization.afterCommit`：

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override public void afterCommit() {
        sseManager.pushToUser(userId, eventName, payload);
    }
});
```

避免"推送已发出但 DB 还没 commit，接收方查询不到"的竞态。

#### 3. SSE async 异常吸收（复用 AI-4 v0.6.2 模式）

```java
emitter.onError((ex) -> log.debug(...));
emitter.onTimeout(() -> log.debug(...));
emitter.onCompletion(() -> log.debug(...));
// SseEmitterManager 内 removeEmitter
```

避免 Spring ErrorPageFilter 输出 "Cannot render error page" 警告。

#### 4. SSE 鉴权（EventSource 不能设 header）

`JwtFilter` 增加 `?t=<token>` 查询参数分支：

```java
if (token == null || token.isEmpty()) {
    String queryToken = request.getParameter("t");
    if (queryToken != null && !queryToken.isBlank()) {
        token = queryToken.trim();
    }
}
```

仅 SSE 端点使用；其他 API 仍走 `Authorization: Bearer`。Token 24h 过期，URL 仅 EventSource 内部使用。

#### 5. 附件两阶段策略

**问题**：`message_attachment.message_id` 有 FK → message.id，不能有孤儿 attachment。

**方案**：
1. upload 仅落盘 + 解析 mime，**不写 DB**，返回 `AttachmentUploadRef {fileName, filePath, fileSize, mimeType}`
2. `sendMessage` 接口接受 `attachments: List<UploadRef>`，写 message 后 `bindToMessage(messageId, refs)` 统一入库
3. sendMessage 失败 → 落盘文件需后续清理（暂未实现 orphan cleanup；20MB 内可接受，后续 v0.7.1 补）

#### 6. 自动已读（双向触发）

`ConversationServiceImpl.open`：
- 拉消息 → 标记对方消息 `read_flag=1`
- 推 `read_receipt` SSE 给对方 → 发送方 UI 显示 "已读"

```
HR 进入会话 → markPeerMessagesRead(conv, HR) → 把候选人消息置 1
            → sseManager.pushToUser(candidateId, "read_receipt", {readerRole: "HR", messageIds: [...]})
            → 候选人侧 Chat.vue onChunk 收到 read_receipt → 本地 msg.readFlag = 1
```

### 关键设计

- **4 维度打分**（Java 内存，bid 优先级）：
  - bit 0（+8）：industryId 命中
  - bit 1（+4）：cityId 命中
  - bit 2（+2）：province 命中（仅 cityId 未命中时计分，避免省份重复 + 城市重复）
  - bit 3（+1）：title / requirements / keywords 三字段任一含任一拆词
- **SQL 宽筛 + 内存打分**：SQL 用 `<choose>` 保证 OR 拼接无悬挂括号，Java 按 score 排序 → 同一分数按发布时间倒序
- **偏好全空降级**：调用前判断 `hasAnyPref`，否则直接走"最新发布"路径，避免无效查询
- **省份二级联动**：省份从 `dict_city.province` 派生去重；切省份自动清空城市（前端避免错配）
