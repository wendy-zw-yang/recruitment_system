## 关键设计要点

### 1. 8 状态机

```java
VALID_TRANSITIONS = {
  PENDING_REVIEW → [VIEWED_BY_HR, REJECTED, WITHDRAWN],
  VIEWED_BY_HR   → [RESUME_PASSED, REJECTED, WITHDRAWN],
  RESUME_PASSED  → [INTERVIEWING, REJECTED, WITHDRAWN],
  INTERVIEWING   → [OFFERED, REJECTED, WITHDRAWN],
  OFFERED        → [HIRED, REJECTED, WITHDRAWN],
  HIRED          → [],  // 终态
  REJECTED       → [],
  WITHDRAWN      → []
}
```

- 终态：`HIRED / REJECTED / WITHDRAWN`
- WITHDRAWN 仅候选人可触发（HR 调 withdraw 接口抛 403；HR 调 pushStatus 也会被合法转换校验拦截）
- 候选人侧列表查询隐藏 `VIEWED_BY_HR`（等同"处理中"）

### 2. 简历快照策略

- 投递瞬间拷贝 `resume.id`（FK 引用）作为 `application.resume_snapshot_id`
- 候选人后续编辑 / 归档 / 删除简历不影响历史投递的快照
- AI-2 评分取快照的当前内容（投递瞬间快照，但评分是异步执行；如快照已被删除则评分失败）
- **不在投递时复制内容到 application 表**：避免数据冗余 + 跟随候选人简历生命周期灵活处理

### 3. AI-2 异步评分

```java
// 投递 HTTP 同步返回（200 + aiScore=NULL）
ApplyResponse resp = svc.apply(candidateId, request);

// 后台异步触发
@Async("taskExecutor")
public void triggerAiScoreAsync(...) {
    LlmScoreService.ScoreResult result = llmScoreService.scoreSync(...);
    onAiScoreCompleted(applicationId, result.score, result.reason);
}
```

- 失败降级：`ai_score` 保持 NULL，HR 端显示"待评分"
- ai_call_log 自动写入（复用 LlmClient.callJson）

### 4. ScorePrompt 草案

```text
SYSTEM:
你是严格的招聘匹配评分专家。基于候选人的结构化简历与职位 JD，给出 0-100 的匹配分与 200 字内的中文评分理由。

评分维度（总和 100%）：
1. 技能匹配度（40%）
2. 经验相关性（30%）
3. 学历 / 行业契合（20%）
4. 加分项（10%）

严格要求：
1. 必须仅返回一个 JSON 对象，不要 Markdown / 解释文字 / 思考块
2. 包含 score (整数 0-100) / reason (string)
3. reason 用中文，2-3 句话
4. 缺失信息视为 0 分项，不得编造事实
```

### 5. 前端轮询替代 SSE

```js
function startAiPolling() {
  let count = 0
  pollTimer = setInterval(async () => {
    count++
    if (count > 15 || !aiPolling.value) { stopAiPolling(); return }
    app.value = await applicationApi.detail(id)
  }, 4000)
}
```

- 4 秒一次 × 15 次 = 60 秒超时
- `aiPolling` = `aiScore == null && status == 'PENDING_REVIEW'`
- §5 消息中心完成后可改 SSE 推送

### 6. 撤回通知降级（按 handoff 2155 决策 #5）

本批**仅写 `application_status_history`**：

```sql
INSERT INTO application_status_history (application_id, from_status, to_status, changed_by, note)
VALUES (?, ?, 'WITHDRAWN', ?, '候选人主动撤回');
```

不发 conversation / message。HR 在收件箱列表可见 `WITHDRAWN` 默认折叠 + 灰色标签（`showWithdrawn` 复选框可展开）。

### 7. HR 列表排序

```sql
-- 默认：AI 评分降序（NULL 排最后），投递时间降序
ORDER BY ai_score DESC, applied_at DESC
-- 可选 sort=applied_desc：仅按投递时间
```

### 8. 简历快照组装（buildResumeJson）

`Resume` 实体的 `education` / `work` / `projects` 字段本身就是 JSON 字符串。`buildResumeJson(Resume r)` 组装成完整结构化 JSON 喂给 LLM：

```java
{
  "basicName": ..., "basicEmail": ..., "basicPhone": ...,
  "selfIntro": ...,
  "education": [...],   // 解析自 r.education JSON 字符串
  "work": [...],
  "projects": [...],
  "skills": [...]       // 按 [,\s;；]+ 拆分 r.skills
}
```

## 追加 · 修复 toggleFavorite 500 bug + 删 banner（12:20）

### 用户第二轮反馈

> 1. 你没有修复收藏的问题，现在点击收藏后，会显示"系统异常，请稍后重试"
> 2. "只看收藏"没什么问题
> 3. "职位浏览"页的"🔍 应用了首页搜索条件"这一行不需要加，只要填写搜索内容并点击搜索即可，把这一行提醒去掉就行
> 4. 求职者前端的职位列表显示不要加一堆"Java 工程师"这种虚假信息，HR发布了哪些职位就显示哪些，所有数据来源都必须可靠（数据库为准）

### 反馈 1 根因诊断：UNIQUE 约束 + 软删除冲突

**完整调用链**：
```
用户点星标 → POST /api/jobs/{id}/favorite
  → JobController.favorite
    → JobServiceImpl.toggleFavorite
      → SELECT 找现存的 favorite_job（is_deleted=0 自动过滤）
      → 若找到 → BaseMapper.deleteById → @TableLogic 软删除（is_deleted=1）
      → 若没找到 → INSERT 新行
```

**Bug 触发路径**（生产环境）：
1. 用户首次收藏 jobId=10 → INSERT 成功（is_deleted=0）
2. 用户取消收藏 → 软删除（is_deleted=1，**行还在表里**）
3. 用户再次收藏同 jobId=10 → SELECT 过滤掉软删行（is_deleted=1）→ 找到 null → INSERT → **UNIQUE 约束 `uk_favorite_candidate_job(candidate_id, job_id)` 冲突 → DuplicateKeyException → 500**

**为什么测试通过**：现有 `toggleFavorite_addAndRemove` 测试在**单事务内** add + remove，整体 `@Transactional` 回滚 → 软删除行从未持久化到 DB → UNIQUE 约束没机会触发。生产跨 HTTP 请求的事务已 commit，软删行真实存在。

### 修复方案

**移除 `FavoriteJob` 的 `@TableLogic`**（让 `deleteById` 走硬删除）：

```diff
- @TableLogic
- @TableField("is_deleted")
- private Integer isDeleted;
```

**为什么是硬删除**：
- 收藏 toggle 是破坏性操作（用户明确"不再收藏"），无需保留审计行
- 表上 UNIQUE 约束 `(candidate_id, job_id)` 是 DB 层硬规则，软删除会导致重新收藏冲突
- 没有其他地方 soft-delete favorite_job

### 反馈 3：删除 banner

直接移除 `<div v-if="fromHomeSearch" class="filter-hint">` 元素 + 对应 CSS + `clearAllFilters` 函数（无 UI 触发）。
仅保留 `fromHomeSearch` computed 作为内部状态变量（保留语义，可能后续埋点用）。

### 反馈 4：数据来源可验证

**全量体检**：JobBrowse / CandidateHome / HrHome / ApplicationInbox 中所有 `v-for` 引用 `records` / `recommendedJobs` / `onlineJobs` 全部来自 `jobApi.list()` / `jobApi.listMine()`，**无任何硬编码假数据**。

**加强可见性**：JobBrowse 顶部 result-meta 区增加小灰字"数据来自 HR 实时发布"，让用户视觉上确认数据可靠性。

**额外 UX bug 顺手修复**：

```diff
- const favorited = await jobApi.toggleFavorite(job.id)
- job.favorited = favorited  // ❌ 赋了 object，不是 boolean
+ const res = await jobApi.toggleFavorite(job.id)
+ const favorited = res?.favorited === true
+ job.favorited = favorited
```

`toggleFavorite` 后端返回 `{jobId, favorited}` 对象，原代码 `job.favorited = favorited` 把整个对象赋给 `job.favorited`，虽然对象 truthy 不影响显示，但语义错误。现只取 `res.favorited === true`。

### 用户清理 DB 操作（修订版）

执行修订后的 SQL，**只清理 (title, province, city_id) 完全相同的职位**：

```sql
USE recruitment_system;

-- 1) 诊断
SELECT title, province, city_id, COUNT(*) AS cnt
FROM job WHERE is_deleted = 0
GROUP BY title, province, city_id HAVING COUNT(*) > 1 ORDER BY cnt DESC;

-- 2) 清理（按 title+省+市 去重）
UPDATE job j
JOIN (
    SELECT MIN(id) AS keep_id, title, province, city_id
    FROM job WHERE is_deleted = 0
    GROUP BY title, province, city_id HAVING COUNT(*) > 1
) dup ON dup.title = j.title
     AND COALESCE(dup.province, '') = COALESCE(j.province, '')
     AND COALESCE(dup.city_id, 0) = COALESCE(j.city_id, 0)
     AND j.id != dup.keep_id

FROM job WHERE is_deleted = 0
GROUP BY title, province, city_id HAVING COUNT(*) > 1;
```
